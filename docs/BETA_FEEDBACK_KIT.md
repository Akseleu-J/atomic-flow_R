# BETA_FEEDBACK_KIT — контент для запуска беты (T2: паки, интейк, фидбек)

Дата: 16.11.2026. Владелец использует этот текст при постинге на форуме и в
формах. Каждая метрика из п.4 плана беты имеет здесь знаменатель — сбор
добровольный через `af evidence export`, тихой телеметрии нет.

## 1. Task-паки (что делает участник за 96 часов)

### Пак 1 — «Первый контакт» (обязательный)
1. Распаковать архив, проверить SHA256, `af doctor` — все строки PASS.
2. `af serve --studio-dist studio` → открыть `/studio/` (loopback).
3. Зарегистрировать свой проект (папку) в Studio, собрать граф.
4. Задать вопрос о проекте в чате. Ожидание: ответ + Verification Summary.
   Без провайдера работает локальный scripted-бэкенд (честный эхо-ответ).

### Пак 2 — «Правка» (основной сценарий инженера)
1. Провайдер: Studio настройки → выбор из каталога (ключ — только имя env-
   переменной; сам ключ остаётся в вашей среде) + `af budget create`.
2. `af task run --root-id ... --file ... --replacement ... --check-argv ...`
   Ожидание: FAIL не трогает исходник; PASS применяет ровно согласованные
   байты; итог — Completed только с зелёным behavioral check.

### Пак 3 — «Наблюдаемый отказ» (проверка безопасности)
1. Запустить задачу с заведомо ломающим проверку replacement.
2. Ожидание: FAIL → исходник не изменён → дистансер объясняет причину.
3. `af evidence export` → приложить пакет к фидбеку.

### Пак 4 — «Бюджет» (короткий)
1. `af budget create --cap-usd 0.01 --max-calls 2` → live-задача сверх капа.
2. Ожидание: отказ admission ДО вызова провайдера; `af budget show` — HOLD.

## 2. Интейк-анкета (клики при подаче заявки)

1. ОС: Windows 10 / Windows 11 / Linux (дистрибутив).
2. Роль: инженер / исследователь / другое.
3. Опыт с CLI-агентами: нет / немного / ежедневный.
4. Язык проекта: Rust / TypeScript / Python / смешанный / другой.
5. Готов ли хостить worker (Linux/KVM) в волне изоляции: да / нет / обсудим.

## 3. Форма фидбека (в follow-up-форум, под каждую волну)

1. Установился с первого раза? (да/нет; если нет — на каком шаге).
2. Время до первого успеха Пака 1: <10 мин / <30 мин / дольше.
3. Пак 2 прошёл? FAIL/PASS-поведения совпали с описанием?
4. Ложные срабатывания проверок: сколько, в чём выражались.
5. HOLD/бюджет-отказы: случились? Понятна ли причина из UI/CLI?
6. Что бросили и почему (самое ценное поле).
7. Приложить: `af evidence export` (пакет без исходников и ключей).

## 4. Метрики волны (считает владелец из бандлов)

- инсталлы → успешные установки → первый успешный сценарий (знаменатель:
  начавшие сценарий);
- время до первого успеха (медиана/p95);
- доли: FAIL-поведения совпали, HOLD-объяснения понятны, evidence-пакеты
  собраны;
- порог расширения волны: ≥10 установок и ≥80% первого сценария среди
  начавших; стоп-условия — по плану беты (утечка / выход гостя / повтор
  неизвестного вызова).

## 5. Порядок стопа и поддержки

- Один канал фидбека (ветка форума на участника); таймбокс окна; владелец —
  ответственный за остановку волны.
- При стоп-условии: отзыв приглашений, новый артефакт, повтор затронутых
  проверок (см. ENGINEER_BETA_PLAN, «Проведение беты»).
