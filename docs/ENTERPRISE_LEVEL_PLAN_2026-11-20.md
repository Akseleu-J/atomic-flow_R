# ENTERPRISE LEVEL PLAN — Atomic Flow, 20.11.2026

Пошаговый план выхода на уровень корпоративных систем агентского кодинга
(Claude Code Enterprise, GitHub Copilot cloud agent, OpenAI Codex, Devin,
Factory). Опирается на `ENTERPRISE_CORE_PLAN.md` (E00–E08), `PRODUCTION_ROADMAP.md`
(P00–P14) и `AUDIT_RESPONSE_2026-11-20.md`. Ничего из этих документов не
отменяет: здесь даны **порядок, планка рынка и критерии приёмки** каждого шага.

Формат шага: **что делаем → артефакт → gate (критерий «готово») → связь с P/E**.
Сроки — оценка для «владелец + агенты», без найма. Пункты, которые без людей
невозможны (внешний pentest, аудитор SOC 2, юрист), помечены 👤.

---

## 0. Что значит «корпоративный уровень» — планка рынка

Сводка того, что лидеры реально продают корпорациям в 2026 году, и где
Atomic Flow сейчас (по коду и докам на `4371834`).

| # | Столп | Что есть у лидеров | Atomic Flow сейчас | Разрыв |
|---|---|---|---|---|
| 1 | **Агентское ядро** | Многошаговый tool-loop, plan mode, subagents, сжатие контекста, checkpoints/rewind, hooks | TurnLoop, guided edit, rewind, enrichment, evidence | Средний: нет hooks, plan mode, subagents, сжатия |
| 2 | **Модель разрешений** | Режимы разрешений; админ задаёт: блокировать / спрашивать / разрешать по типам операций [1][3] | Envelope-авторизация (ADR-0001), fail-closed эффекты | Средний: нет пользовательских режимов и политик |
| 3 | **Управляемые настройки** | Managed settings важнее локальных; доставка через консоль/MDM/файл [1][2] | Нет | Большой |
| 4 | **Identity** | SSO (SAML/OIDC), SCIM, seat-управление [1] | Single-owner, bearer-токен | Большой (E03) |
| 5 | **Изоляция исполнения** | Песочница на уровне ОС у Codex [16]; эфемерные VM на сессию у Devin [5]; firewall агента у Copilot [3] | Docker или local-trusted; Firecracker не принят | Большой (P10, Ф-3) |
| 6 | **Egress и защита от injection** | Org-level firewall агента [3]; MCP governance [4] | Нет egress-политики | Большой (E05) |
| 7 | **Аудит и наблюдаемость** | Compliance API + audit log + OTel-метрики (токены, стоимость, пользователь) [1][2] | Журнал с хеш-цепочкой, evidence export, `af doctor` | Средний: нет экспорта для SIEM и OTel |
| 8 | **Фоновые / облачные агенты** | Агент по issue → PR; управление из app/CLI [3][4] | Нет | Большой |
| 9 | **Модели развёртывания** | SaaS, single-tenant VPC, in-VPC, air-gapped [5][6] | Локальный бинарь; сервер — опция | Большой (P11, E08) |
| 10 | **Стоимость и квоты** | Аналитика расходов по пользователям и командам | Нанодолларовый ledger с hold — **сильнее среднего** | Малый: нужна иерархия орг→проект→пользователь |
| 11 | **Supply chain** | Подписанные релизы, SBOM, provenance | SBOM; release.yml сломан (К-3); без подписи | Средний |
| 12 | **Комплаенс** | SOC 2 Type II, ISO 27001, ISO 42001 [5][6] | Нет | Большой, 👤 |
| 13 | **Интероперабельность** | MCP с OAuth 2.1 + enterprise-managed authorization [7]; ACP для редакторов [8] | `mcp.rs` и `mcp_stdio.rs` (stdio) | Средний |

**Где Atomic Flow уже сильнее рынка** — это и есть суть, которую сохраняем:
1. Детерминированный журнал + evidence + честные вердикты (E01). Лидеры
   признают, что их Compliance API **не видит всех tool-вызовов и локальных
   команд** [2]. AF может видеть всё — по построению.
2. Fail-closed семантика эффектов и запрет replay неизвестных вызовов.
3. Точный учёт денег с hold-семантикой.
4. Граф понимания кода (UA) с контекстом, учитывающим влияние правок.

**Стратегия:** не догонять UI. Строить **«проверяемого агента»**: всё, что он
сделал, доказуемо третьей стороне. Корпоративные функции (SSO, политики,
аудит) встраиваются в это ядро, а не прикручиваются сбоку.

---

## 1. Неизменяемые принципы

1. Сохраняются протоколы `ATOMIC_FLOW_PROTOCOLS_MASTER.md`: секреты только
   в vault, полный цикл «тест → fmt → clippy → CI», обе ветки.
2. Журнал принадлежит хосту. Переписка не копируется на сервер без явной
   политики.
3. Без молчаливых fallback'ов: «не изолировано» никогда не выдаётся за
   «изолировано», `not_assessed` — никогда не за PASS.
4. Отказ по умолчанию для неизвестных действий, scope'ов и цен.
5. Каждая фаза закрывается gate'ом **с доказательствами** (evidence-хеши в
   реестре приёмки). Нет доказательства — фаза OPEN.

## 2. Фазы

```
Ф0 Доверие ─► Ф1 Бета+измерения ─► Ф2 Ядро агента ─► Ф3 Политики и аудит
   (1 нед)       (3-4 нед)            (2-3 мес)          (2-3 мес, параллельно с концом Ф2)

               Ф6 Комплаенс ◄── Ф5 Развёртывания ◄── Ф4 Мультипользовательский сервер
               (6-12 мес, 👤)    (2-3 мес)              (3-4 мес)
```

Реалистичный горизонт до первого корпоративного пилота (Ф0–Ф4, частично Ф5) —
**8-10 месяцев**. До SOC 2 Type II — **+6-12 месяцев** наблюдательного периода
аудитора.

### Ф1. Бета волны 1 и базовые измерения — 3-4 недели

Без цифр нельзя доказать «уровень лидеров». Измерения начинаем сейчас, а не
после фич.

| Шаг | Что делаем | Артефакт / Gate |
|---|---|---|
| 1.1 | Схема пропуска v2: `activate_by`, `hard_expires_at`, CRL на статическом хостинге (А-1, А-2) | Пачка пропусков из CSV одной командой |
| 1.2 | Подписанные `SHA256SUMS` (minisign), GitHub release, форма фидбека с файлом, `af feedback bundle` (А-4, А-5) | Полный цикл на 2 тестерах |
| 1.3 | **Eval-стенд:** адаптер AF для Harbor (harness Terminal-Bench 2.0) [9]; подмножество SWE-bench Verified/Pro [9]; собственный корпус из P07 | `eval/` с фиксированными версиями задач, k≥3 прогона |
| 1.4 | **Базовая линия:** та же модель, те же задачи — AF против Claude Code / Codex CLI / OpenHands (все поддерживаются Harbor) [9] | Таблица: решено %, $/задачу, время, вмешательства |
| 1.5 | Учёт метрик в журнале (P08): задержки по фазам, задержка отмены, токены, кэш | Поля в evidence, ограниченные по размеру |
| 1.6 | N07-бенчи: счётчики инструкций в CI (детерминированно), wall-clock — на Kaggle | Регрессия >5% валит CI |
| 1.7 | Рассылка волны 1 (20-50 человек), сбор `beta-final-report` | ≥15 отчётов, сводка `af feedback summarize` |

**Gate Ф1:** есть **честная базовая линия** против 2+ лидеров на одном
наборе задач, и бета-цикл работает без ручного вмешательства владельца.

### Ф2. Ядро агента уровня лидеров — 2-3 месяца

Цель — паритет **возможностей** однопользовательского агента. Это не копия
чужого UI. Порядок — по соотношению ценность/стоимость.

| Шаг | Что делаем | Обоснование / источник | Gate |
|---|---|---|---|
| 2.1 | **Режимы разрешений** (`ask` / `accept-edits` / `plan` / `auto` / `deny`) поверх envelope из ADR-0001; каждый инструмент — отдельная сущность с разрешением | Публичные разборы архитектуры Claude Code: каждый инструмент проходит через разрешение [10] | Матрица «режим × инструмент», тесты обхода |
| 2.2 | **Hooks** (pre/post tool, on-stop, on-session-start): внешние процессы с таймаутом и лимитом вывода; результат — решение или блокировка | Стандарт индустрии; основа корпоративных политик | Hook не может расширить права, только сузить |
| 2.3 | **Песочница ОС по модели Codex**: единый API «команда + профиль разрешений»; Linux — Landlock+seccomp, macOS — Seatbelt, Windows — restricted token [16][17] | Убирает зависимость от Docker у участника (сейчас `docker FAIL → local-trusted`) | Escape-тесты на 3 ОС; local-trusted только явно |
| 2.4 | **Plan mode**: read-only исследование → план → подтверждение → исполнение | Снижает число вмешательств | План — артефакт в журнале |
| 2.5 | **Сжатие контекста** по ACE (инкрементальные структурированные дельты вместо полного переписывания summary) [11] | Полное переписывание вызывает «context collapse» [11] | Длинная сессия не теряет решений (тест на P09-сессиях) |
| 2.6 | **Subagents** с изолированным контекстом и **урезанными** правами; результат — evidence, а не текст | Параллелизм без утечки контекста | Субагент не может получить больше прав, чем родитель |
| 2.7 | **MCP-клиент**: stdio + streamable HTTP; OAuth 2.1 с RFC 8707 resource indicators; без проброса токенов [7] | Спецификация MCP 2026-07-28 [7] | Conformance-тесты; токен привязан к одному серверу |
| 2.8 | **Git/PR-поток**: ветка на задачу, коммиты с evidence-ссылками, PR с отчётом верификации | Основной корпоративный сценарий [3] | PR содержит VerificationReport |
| 2.9 | **Headless/CI-режим**: `af run --headless --policy <file>` для GitHub Actions/GitLab CI, JSON-поток событий | Основа для фоновых агентов Ф4 | Пример workflow в репо проходит |
| 2.10 | **ACP-сервер** — Zed, JetBrains, Neovim получают AF без своего UI [8] | Дешёвый охват редакторов | Работает в Zed |
| 2.11 | Studio: только то, что уникально для AF (evidence, бюджет, rewind, граф) | Не тратить силы на копию чужого UI | Г-2 закрыт по референсу владельца |

**Gate Ф2:** на стенде из Ф1 AF с той же моделью отстаёт от лучшего
эталонного harness'а не больше чем на **X п.п.** (X фиксирует владелец до
замера; ориентир — ≤5). При этом не нарушен ни один контракт безопасности
(no-replay, fail-closed, честные вердикты).

### Ф3. Политики, egress, аудит — 2-3 месяца (стартует с середины Ф2)

Это то, что покупает служба ИБ. Здесь AF может **обойти** лидеров за счёт
журнала.

| Шаг | Что делаем | Обоснование / источник | Gate |
|---|---|---|---|
| 3.1 | **Policy engine на Cedar** (Rust-крейт `cedar-policy`, отказ по умолчанию, валидация схемы, формальная модель на Dafny) [12] — реализует порт `PolicyEngine` из E00/E03 | Не писать свой язык политик; Cedar проверен в AWS Verified Permissions | Все решения разрешений идут через движок; версия политики записывается в журнал |
| 3.2 | **Иерархия управляемых настроек**: организация > проект > пользователь; подписанный бандл политик (ed25519, тот же инструментарий); доставка файлом/MDM, позже с сервера | Как managed settings у Claude Code и Copilot [1][3] | Пользователь не может ослабить политику организации |
| 3.3 | **Egress-firewall**: allowlist доменов для инструментов, MCP и моделей; проверка **до** вызова (E05.2) | Org-level firewall у Copilot cloud agent [3] | Канарейки секретов не покидают хост |
| 3.4 | **Защита от prompt injection по дизайну**: метки происхождения на выходах инструментов (trusted/untrusted); данные с меткой untrusted не могут влиять на поток управления и вызовы с эффектами без подтверждения — паттерн CaMeL / Dual LLM [13] | Фильтры не решают injection; решает разделение потока управления и данных [13] | AgentDojo-подобный набор: эксфильтрация через вредоносный README блокируется |
| 3.5 | **Secret broker**: короткоживущие гранты на операцию; секреты не попадают в журнал и архивы (E05.3) | — | Сканер секретов по журналам = 0 находок |
| 3.6 | **Журнал → Merkle-лог (C2SP tlog-checkpoint / signed-note)**: per-event листья, подписанные checkpoint'ы, cosign при экспорте [14] | Закрывает same-size окно, retention и даёт аттестацию для B2B (Ф-2 аудита) | Доказательство включения отдельного события проверяется сторонним верификатором |
| 3.7 | **OTel GenAI-трассы**: `invoke_agent` → `chat` / `execute_tool`; содержимое по умолчанию не пишется [15] | Конвенции пока в статусе Development — версию зафиксировать [15] | Трассы видны в Jaeger/Grafana; нет PII в атрибутах |
| 3.8 | **Экспорт аудита для SIEM**: JSONL/OCSF-подобный поток решений политик, эффектов и вызовов моделей | Пробел лидеров: их API не видит всех команд [2] | Каждый tool-вызов есть в экспорте, сверка с журналом 1:1 |

**Gate Ф3:** сквозной сценарий «вредоносный репозиторий + секрет-канарейка +
запрещённый домен + отзыв политики посреди задачи». Нет утечки, нет эффекта
после отзыва, всё видно в аудите (= gate E05 + часть E03).

### Ф4. Мультипользовательский сервер (Corporate core) — 3-4 месяца

Профиль «Corporate core» из `ENTERPRISE_CORE_PLAN` §1.

| Шаг | Что делаем | Связь | Gate |
|---|---|---|---|
| 4.1 | **Порты хранилища** (E00): `TaskRepository`, `EvidenceStore`, `BudgetService` и др.; реализации SQLite (локально) и **PostgreSQL** (сервер) | E00, E04.8 | Один сценарий проходит на обоих бэкендах |

| 4.7 | **Изоляция worker'ов**: gVisor (systrap, без KVM) по умолчанию [18]; Firecracker на хостах с KVM; одна VM/контейнер на сессию, уничтожается после [5] | P10, B4a | Escape-набор + сетевой egress по политике Ф3 |
| 4.8 | **GitHub App / GitLab-интеграция**: минимальные права, токены на установку | — | Права App задокументированы и минимальны |
| 4.9 | **Админ-API и консоль**: пользователи, политики, бюджеты, аналитика (принятие правок, стоимость, вмешательства), экспорт аудита | E07 | Админ без shell-доступа управляет всем |
| 4.10 | **MCP governance**: реестр одобренных серверов по дайджесту, enterprise-managed authorization через IdP [4][7] | E06.5-6 | Неодобренный MCP-сервер не запускается |

**Gate Ф4 = E08 (corporate profile):** независимый потребитель поднимает
сервер из артефактов, подключает IdP и модель по инструкции, двое
пользователей проходят полный цикл «понимание → план → правка → тесты →
одобренный PR». Проверены ACL, квоты, отмена, отзыв, рестарт и восстановление.

### Ф6. Assurance и комплаенс — 6-12 месяцев (параллельно с Ф4–Ф5)

| Шаг | Что делаем | Gate |
|---|---|---|

## 5. Риски и kill-критерии

| Риск | Сигнал | Действие |
|---|---|---|
| Отставание качества от лидеров не сокращается | После Ф2 разрыв > X п.п. на стенде | Перенести фокус на Ф7.2 (harness) и Ф3 (ниша «проверяемости»), не на паритет фич |
| Распыление: соло-разработка 7 фаз | Две фазы одновременно больше 2 недель | Жёсткий WIP-лимит: одна фаза в работе + один фоновый поток |
| Песочница на Windows сложнее ожидаемого | Escape-тесты не проходят за 3 недели | Windows: только WSL2 + Linux-песочница; нативная — позже |
| Спецификации плывут (OTel GenAI, MCP) | Breaking-изменения | Версия фиксируется в адаптере; conformance-тесты на версию |
| Комплаенс дорогой для соло-владельца | Нет бюджета на аудитора | Сначала «SOC 2-ready» (контроли + доказательства), сертификация — под первый платящий контракт |
| Юридический риск утёкшего кода | Любой заимствованный фрагмент | Только публичные разборы архитектуры и OSS с совместимой лицензией (Codex — Apache-2.0) |
